Architecture Bottleneck

The Problem: Cloud Composer 10GiB Worker Eviction

Why traditional PythonOperator in-worker decompression fails on enterprise banking flat files
⚠️ The Celery Worker Disk Bottleneck

In standard Airflow implementations, files are pulled to local /tmp and extracted directly on the Celery Worker node using PythonOperator or in-line Python scripts.

In Cloud Composer Gen 2 (GKE Autopilot), worker pods operate with a hard root filesystem limit of 10239Mi (~10 GB).

  • Files >10 GB exceed worker rootfs storage immediately.
  • Kubelet fires SIGTERM eviction signal to kill the worker.
  • Entire Celery Worker crashes, aborting all concurrent DAG tasks.

💥 Failure Mechanics Breakdown
1. Ingestion Layer: External SFTP deposits 15GB raw transactions into Landing GCS Bucket.
2. Worker Saturation: Celery Worker begins downloading and decompressing archive to local /tmp.
3. Kubelet Eviction: At 10.00 GB, storage exceeds the 10239Mi limit. GKE Autopilot daemon sends SIGTERM.
4. Cascade Failure: Worker container crashes, killing unrelated workflows on that node.

Approach 2 Architecture

Pod-Offloaded Zero-Disk Streaming (Scales to 100GB+)

Discrete GKE Autopilot Pod with direct GCS-to-GCS streaming via native C Zlib
🚀 Architectural Advantages
1. Control Plane Isolation: Composer Worker holds 0 MB RAM/Disk load; only tracks pod heartbeat.
2. Zero-Disk C-Streaming: Reads from Landing GCS, streams through native C Zlib, and writes 64MB multipart chunks directly to Staging GCS.
3. Least Privilege IAM: Runs under dedicated Kubernetes Service Account (KSA) with Workload Identity.
4. Clean Auto-Cleanup: Pod is automatically destroyed on completion (is_delete_operator_pod=True).
